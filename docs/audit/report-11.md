## 需要改动的地方

### 1. 告密者（中）

- **文件/位置**：`engine.cjs` `dealEvilInfo()`（第 572 行），具体在第 576-588 行拼信息文本处。
- **改成什么**：给爪牙的那条信息里追加三个伪装。现在走 `evilInfoFor()`（第 550 行）→ 爪牙只得到「你的同伴是：<恶魔>（恶魔）」（第 579-581 行），而 `bluffRoles(id)`（第 563 行）算出的三个伪装只拼进恶魔那条（第 584-588 行）。应在爪牙分支里复用 `bluffRoles(id)` 取三个角色名，拼成「你的同伴是：X（恶魔）；你可以伪装成的三个身份：A、B、C」。
- **为什么**：告密者的能力原文就是「爪牙会在其首个夜晚得知三个伪装」，而现有实现把三个伪装独占了给恶魔。同时 `agents.cjs:506` 的夜间提示词写着「爪牙信息/恶魔信息已自动完成，不要重复」，说书人被告知不要补发，于是这条信息在程序模式下永久缺失；手工兜底要绕过提示词才行，所以定中而不是高。

### 2. 哈迪寂亚（高）

- **文件/位置**：`agents.cjs` `buildStorytellerNightPrompt()`（第 446 行）第 455 行的硬规则 + 输出 schema（第 512-518 行）；`agents.cjs` `runStoryteller()` 等待循环第 1026-1042 行与 apply 块第 986-1017 行。
- **改成什么**：
  1. 第 455 行「绝不能在公聊里说出你夜里唤醒了谁」需要有条件放行：当在场恶魔是哈迪寂亚时改为「必须公开说出你选了哪三名玩家（但不得说他们各自的生死决定）」。
  2. 回包 schema 增加 `publicInfo` 字段（字符串数组），apply 块里用 `E.say(id,'storyteller',text,'town')` 广播，而不是塞进只对单人可见的 `info[]`。
  3. 增加 `secretChoices` 之类的字段承载「每个被问者自己的存活/死亡选择」，并把等待循环从 `fresh.some(...)`（任一回复即继续）改为等齐全部被问者或超时。
  4. 增加结算钩子：三名被选者的选择都收集完后判断「三人全部选择存活 → 三人全部死亡」，再转成 `deaths[]` 交给 `kill()`。
- **为什么**：这是本批唯一一个「能力本身无法表达」的角色。三件事都不是措辞问题：公开信息是能力硬性要求（所有玩家都会得知），同时秘密决定需要按人记录（现在只有自由文本私聊，且任一回复就继续，后回复的人会被丢掉），条件群杀需要统一结算（现在没有任何地方做这个判断）。不改则整条能力无法执行。

### 3. 哥布林（高）

- **文件/位置**：`engine.cjs` `checkWin()`（第 253-277 行）、`execute()`（第 176-182 行）、`endGame()`（第 279-285 行）；`agents.cjs` 夜间 schema（第 512-518 行）、白天 schema（第 548 行）、apply 块（第 986-1017 行）。
- **改成什么**：
  1. `engine.cjs` 在 `execute()` 里加判定：若被处决座位带「已公开声明哥布林」标记且其角色为哥布林 → 直接 `endGame(id,'evil')`，不要走普通的死亡流程。
  2. 回包 schema 增加 `endGame: 'good'|'evil'|''` 与 `endReason`，apply 块里调用 `E.endGame`（现在 replay 里根本没有这个字段，说书人无法结束游戏）。
  3. `server.cjs buildApi`（第 35-172 行）新增 `declare` 端点，`public/app.js` 加「公开声明」按钮，给该座位打 `声明:哥布林` 标记并在公聊播报。
- **为什么**：哥布林的能力不是被动信息，而是一条新的胜负判定。现有胜负逻辑写死在 `checkWin()` 里，只有「恶魔离场 → 善良胜」和「存活≤2 且恶魔在 → 邪恶胜」两条；说书人代理既没有终局字段也不能改胜负，公开声明后在白天被处决只会走 `execute()` 变成一具尸体，游戏继续。这是硬编码覆盖导致规则错，定高。

### 4. 唱诗男孩（中）

- **文件/位置**：`engine.cjs` `kill()`（第 227-238 行）与 `execute()`（第 176-182 行）；`data/nightorder.json` other 表第 183 行（唱诗男孩）与第 206 行（国王）。
- **改成什么**：
  1. `kill()` 记录死因与来源，例如 `s.deathLog.push({seat, cause:'demon', by})`，或至少在 `kill(id, seat, reason)` 的 reason 里带上凶手座位；再加一个判定：若死者角色为国王且在场有唱诗男孩 → 给唱诗男孩发「X 号是恶魔」。
  2. `data/nightorder.json` 把唱诗男孩在 other 表的位置挪到国王之后（第 206 行之后），否则当晚国王被杀时唱诗男孩这一轮已处理完，反应时机永远错位。
  3. `data/roles.json` 唱诗男孩条目补一致性（first_night 为 true 但 first 表无条目，属文档不一致，可顺手补）。
- **为什么**：`[+国王]` 的强制配牌是能跑通的（`dealRoles` 第 467 / 486-501 行按 `extraRoles` 塞进 reqTown），所以问题不在配牌；真正的卡点是「恶魔杀死国王」这个触发条件全代码没有任何记录——`kill()` 只有 `s.alive[seat]=false`、`markers` 推「死亡」、`nightDeaths` 记录，没有凶手也没有钩子。加上顺序错位，这一夜必然漏触发。因为说书人掌握全部真值、次日可以补发，所以定中。

### 5. 园丁（中）

- **文件/位置**：`engine.cjs` `dealRoles()` 牌池构造（第 452-454 行）；`engine.cjs` `setRoleMode()`（第 623 行）/ `createAndStart()`（第 603 行）。
- **改成什么**：
  1. 在 `dealRoles()` 牌池里显式支持 `loric`（奇遇角色）组——现有只读 镇民/外来者/爪牙/恶魔 四组；或按 `docs/audit/report-17.md` 的建议新增 `addTraveler(id, seat, role)` 之类的入场函数。
  2. 在 `dealRoles()` 入口加判断：若牌堆中含园丁，强制 `s.roleMode='storyteller'` 并跳过机械发牌，改由说书人逐人给出「你的角色是【X】」（该路径已存在于 `agents.cjs:491`）。
- **为什么**：园丁的能力语义是「说书人取代程序发牌」。程序发牌模式下它自己就是程序发出来的，逻辑自相矛盾；而且当前牌池按四组过滤，loric 组根本抽不到，园丁连进场机会都没有。能力与机制不冲突（说书人发牌通道存在），所以是中不是高。

### 6. 国王（低）

- **文件/位置**：`agents.cjs` `buildStorytellerNightPrompt()` 座位表（第 473-481 行）与规则区（第 493-505 行）。
- **改成什么**：在座位表或规则区直接给出派生数值，例如「当前死亡 N 人 / 存活 M 人（死亡数≥存活数：是/否）」，让模型不必自己数；其余不动。
- **为什么**：能力是纯信息（死亡≥存活时得知一个存活角色），两张表里位置都在信息区块内、顺序正确，`info[]` 完全可以表达。唯一风险是 LLM 数错人数导致信息错误，属体验/可靠性问题，定低。

### 7. 堤丰之首（中）

- **文件/位置**：`engine.cjs` `bracketSpec()`（第 399-425 行，`anyOutsider` 第 401/473/478 行）与 `dealRoles()` 邪恶邻座布局（第 513-517 行）；`data/roles.json` 第 1558-1570 行。
- **改成什么**：
  1. 第 513-517 行的 `const start = Math.floor(Math.random() * n)` 后加居中逻辑：当能力文本含「正中」时把邪恶块起始座位算成 `Math.floor((n - evilCount)/2)`，使恶魔落在中间座位；否则维持随机。
  2. `anyOutsider` 目前是死变量（全代码只有第 401/412/473/478 行的赋值与置位，无读取）。要么在 `dealRoles` 里真正消费它（外来者数量交给说书人任选），要么给 `bracketSpec` 加显式的「说书人选择外来者数量」字段并在 `/api/dealRoles` 里透传；同时修第 401 行的括号解析——整段长括号会作为一个 tag 传入，`[-−]\s*(\d+)\s*外来者` 匹配不上「-或+任意数量外来者」。
  3. `data/roles.json` 第 1562 行附近把 `first_night` 改为 false（能力是「每个夜晚*」，即从第二夜起）。
- **为什么**：每夜杀人可以正常执行（`deaths[]` → `kill()` 链路完好），所以不是高；但开局配置三项被静默吞掉：「你靠近正中」在 engine.cjs 里 0 命中、邪恶角色永远是随机连续座位；「-或+任意数量外来者」因为括号内没有数字匹配不上、且 `anyOutsider` 变量根本没被消费；first_night 标志与能力原文自相矛盾（不过这些 flag 实际无人读取，属文档一致性）。

### 8. 失忆者（中）

- **文件/位置**：`engine.cjs` `giveInfo()` 角色正则（第 143-144 行）；`agents.cjs` apply 块第 992-994 行的重复分配拦截；`agents.cjs` `buildStoryChatPrompt()`（第 1320-1350 行）。
- **改成什么**：
  1. 提供「伪能力」承载方式：发信息时用「你的能力是：……」而不是「你的角色是【X】」，避开第 143-144 的正则与 `agents.cjs:992-994` 的字面量拦截。
  2. 在 `s` 上（或 markers）记录伪能力文本与「今日是否已猜」：`toggleMarker` 只能开关不能存值，建议新增 `s.amnesiac = {ability, guessedDay}`。
  3. 白天猜测走 `buildStoryChatPrompt` 私聊通道即可，但要在白天提示词（第 525-550 行）里告诉说书人「失忆者今天的猜测是 X，请按其伪能力给出准确度」，否则说书人不知道要回答什么。
- **为什么**：程序模式只挡字面量「你的角色是【X】」，换个措辞就能把伪能力传下去，所以能力不是完全无法执行；真正缺的是「每白天一次猜测 + 准确度回答」的固定流程和「已猜过」的状态，目前全靠私聊自由文本，说书人可能忘记或重复回答，故定中。

### 9. 失败的上帝（中）

- **文件/位置**：`engine.cjs` `createGame()` 的 state 结构（第 41-49 行）与 `toggleMarker()`（第 287-292 行）。
- **改成什么**：在 state 里加一个一次性槽，例如 `s.legendary = {failedGodUsed:false}`，并在说书人提示词（夜间第 493-505 行 / 白天第 525-550 行）里注入「失败的上帝在场且尚未触发：本局你至少需要一次公开承认处理失误」；公开纠正本身用现有 `say()`（`engine.cjs:298`，白天公聊）即可。
- **为什么**：它没有夜间动作，两张 nightorder 表都没有它是对的；卡点纯粹是状态承载——「每局至少一次」需要跨回合的一次性标记，而 `state.markers` 是 `seat -> string[]` 的开关数组，无值、无 TTL、无「已用」语义，`toggleMarker` 也只做 push/splice。加上这句要求对说书人是软约束、无法自动校验，故定中。

### 10. 奥赫（低）

- **文件/位置**：`agents.cjs` `buildStorytellerNightPrompt()` 座位表（第 473-481 行）；`data/nightorder.json` other 表第 150 行；`data/roles.json` 第 1597-1609 行。
- **改成什么**：
  1. 在夜间提示词里给出「在场角色 → 座位」的反查表（座位表已有 角色=… 一列，可再加一行汇总），并写明「奥赫选的是角色不是座位；该角色不在场时由你决定死者」。
  2. `data/roles.json` 第 1601 行附近 `first_night` 改为 false（能力是「每个夜晚*」），与堤丰之首同一条一致性问题。
- **为什么**：伤害结果可以用既有 `deaths[]` → `kill()` 表达，角色到座位的映射在座位表里也看得见，说书人本来就被赋予「角色不在场时自行决定」的裁量权，所以能跑。剩下的只是提示词不够明确（模型可能把「选一个角色」当成「选一个座位」）与 flag 不一致，属措辞/体验问题，定低。

## 附：本批共性结论

- 10 个角色的 `data/roles.json` 条目里 `scripts` 全为 `[]`，三个官方剧本（暗流涌动 / 梦殒春宵 / 黯月初升）的角色清单都不含它们，因此程序发牌在默认剧本下永远不会把这些角色发进场——这是本批多数问题「处于休眠状态」的根因，但每个角色的判定仍按「一旦进场」评估。
- `first_night` / `other_nights` / `on_death` 三个 flag 在 engine.cjs / agents.cjs / server.cjs / public/app.js 中零读取，夜间顺序完全由 `data/nightorder.json` 决定（`agents.cjs:434-445`）。所以 flag 写错只影响文档一致性，不影响运行；反之 nightorder 里缺条目才是真的不执行。
- `loric` / `legendary` 两组不在 `dealRoles` 牌池里（只取 镇民/外来者/爪牙/恶魔），与 `docs/audit/report-17.md` 对奇遇角色的结论一致：需要一个入场通道。
